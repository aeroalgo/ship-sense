## 1. Протокол подключения (Q1) — БЛОКЕР ФАЗЫ 1

**Почему критично:** архитектура collector'а разбита на два плагина — `B2 ModbusTCP` и `B3 OPC UA`. Выбор боевого протокола определяет, какой плагин идёт в production-конфигурацию; второй остаётся платформенным, но не первичным.

**Вопросы:**

1.1. Какой протокол является основным для внешнего read-only доступа к данным АПС: **Modbus TCP**, **OPC UA**, или оба предоставляются одновременно?

1.2. Если предоставляется только один — есть ли какой-либо альтернативный/резервный путь (файловый экспорт, другой протокол, промежуточный шлюз)?

1.3. Если оба доступны — одинаков ли состав данных в обоих протоколах, или Modbus и OPC UA содержат разные наборы тегов, разные частоты обновления, разное качество данных?

1.4. Какой протокол Канонерка рекомендует использовать для интеграции внешней аналитической системы (не SCADA, не замена АПС, только read-only архивирование)?

1.5. Есть ли уже действующие внешние клиенты, читающие данные из АПС по одному из этих протоколов? Если да — на каком протоколе и без каких проблем?

## 2. Гарантия Read-Only (I1) — БЛОКЕР ФАЗЫ 1

**Почему критично:** юридически и эксплуатационно ShipSense должен быть доказуемо вне контура управления. Это должно быть не декларацией, а технически верифицируемым фактом.

**Вопросы:**

2.1. Каким именно механизмом гарантируется, что внешний клиент **физически или логически не может записывать** данные в АПС через предоставленный интерфейс?

2.2. Есть ли отдельная read-only роль, учётная запись, сертификат или endpoint, разрешающий только чтение?

2.3. Если протокол — OPC UA: какой `SecurityMode` и `SecurityPolicy` используются, требуется ли клиентский сертификат, и можно ли выдать шаблон/инструкцию по trust store?

2.4. Если протокол — Modbus TCP: какие `function codes` физически доступны внешнему клиенту? Читаются только `FC03`/`FC04`, или клиент технически может послать `FC06`/`FC16`?

2.5. Что Канонерка может предоставить в качестве документального подтверждения изоляции «только чтение», пригодного для предъявления при приёмке РМРС или судовладельцем?

## 3. Карта сигналов native_id ↔ KKS (Ф0) — БЛОКЕР ФАЗЫ 1

**Почему критично:** без этого файла collector работает только со stub-картой (~50 репрезентативных тегов), построенной по таблицам РД. Боевое подключение к АПС требует полной карты.

**Вопросы:**

3.1. Просим передать полную карту соответствия. Для каждого сигнала нужны следующие поля:

| Поле | Пример | Обязательность |
|------|--------|----------------|
| KKS | `TAI4101` | обязательно |
| Человекочитаемое имя | «Температура масла ГД, вкладыш 1» | обязательно |
| Источник | АПС / СКТ ГЭУ | обязательно |
| Native ID в протоколе | Register `40001` / NodeId `ns=2;i=1001` | обязательно |
| Тип данных | `float32`, `int16`, `bool`, bitfield | обязательно |
| Единица измерения | °C, бар, об/мин | обязательно |
| Byte order / Word order | Big-Endian / AB CD | обязательно для Modbus |
| Масштаб / коэффициент | 0.1, /100 | если есть |
| Допустимый диапазон | 0…150 | если известен в АПС |
| Тип сигнала | аналоговый / дискретный / счётчик / статус | обязательно |
| Семантика | если из KKS неочевидно | при необходимости |

3.2. Если карта существует в электронном виде (Excel, XML, CSV, OPC UA NodeSet, Modbus mapping table) — просим передать файлом, а не копировать вручную.

3.3. Сколько всего сигналов реально экспонируется наружу через протокол? Совпадает ли это с ~586, зафиксированными в документации (АПС ~482 + СКТ ГЭУ ~104)?

3.4. Есть ли сигналы, которые присутствуют в документации, но **не публикуются** по протоколу (внутренние, зарезервированные, аппаратные)? Просим перечислить исключения.

3.5. Есть ли сигналы, которые **публикуются**, но отсутствуют в переданной нам документации?

## 4. Формат данных — типы, кодирование, endianness (Ф0) — БЛОКЕР ФАЗЫ 1

**Почему критично:** decoder'ы в collector'е написаны на основе предположений из РД. Без подтверждения есть риск неверной интерпретации значений.

**Вопросы:**

4.1. Какие типы данных используются в вашей системе? Просим подтвердить или дополнить список:
- `bool` / `coil`
- `int16` / `uint16`
- `int32` / `uint32`
- `float32` (IEEE 754)
- `float64`
- Bitfield / bitmask
- Строки (если есть)
- Перечисления (enum-значения)

4.2. Для каждого типа данных в Modbus — какой byte order и word order используется? Примеры:
- `ABCD` (Big-Endian, standard)
- `CDAB` (Big-Endian, word-swapped)
- `BADC` (Little-Endian, byte-swapped)
- `DCBA` (Little-Endian, standard)

4.3. Для float32-значений — какие паттерны возникают при отсутствии сигнала или неисправности датчика? Возможны ли `NaN`, `Inf`, специальные bit patterns?

4.4. Для bitmask/bitfield — как именно раскладываются биты? Просим предоставить описание для каждого такого регистра/тега: что означает бит 0, бит 1 и т.д.

4.5. Для дискретных сигналов — как кодируются `true`/`false` (1/0, или иное)? Есть ли инверсия на каком-либо типе сигналов?

4.6. Если используются масштабирующие коэффициенты — передаются ли они единым списком или описаны в карте регистров (см. п.3)?

4.7. Для перечислений (statuses, modes) — просим предоставить таблицу: числовое значение → инженерный смысл.

## 8. События, тревоги и жизненный цикл (Q4) — БЛОКЕР ФАЗЫ 1

**Почему критично:** журнал событий (Экран 5) и lifecycle-колонки — ключевая ценность для смены экипажа. Без понимания семантики событий на стороне АПС мы работаем в режиме «реконструкции по битам», что честно показываем пользователю с пометкой `reconstructed`, но это деградированный режим.

**Вопросы:**

8.1. Существует ли в АПС **нативный поток событий** (event stream), доступный внешнему клиенту? Или наружу видны только текущие значения дискретных сигналов, из которых жизненный цикл придётся реконструировать у нас?

8.2. Если события доступны нативно — просим описать полный контракт события. Какие поля присутствуют:
- Тип события (тревога, предупреждение, защита, команда, диагностика)
- Код/ID события
- Timestamp источника
- Источник (контроллер, подсистема, узел)
- Severity / Priority / Class
- Состояние: active / acknowledged / cleared / suppressed
- Текст сообщения
- Оператор (кто квитировал)
- Correlation ID (связь между стадиями одной тревоги)
- Любые дополнительные атрибуты

8.3. Если нативного event stream нет — для каждого типа тревоги/события просим указать:
- Какой тег / регистр / NodeId означает «тревога активна»
- Какой тег означает «квитировано»
- Какой тег означает «снято / нормализовано»
- Возможна ли однозначная реконструкция lifecycle по этим состояниям
- Есть ли случаи, когда несколько тревог разного типа «смешиваются» в одном битовом слове

8.4. Каков полный жизненный цикл тревоги в АПС? Просим схему переходов:
```
Создана → Активна → Квитирована → Снята / Нормализована → Закрыта
```
Какие промежуточные состояния существуют? Можно ли тревогу квитировать до снятия? Можно ли снять без квитирования?

8.5. Есть ли автоматическое квитирование / автоматическое снятие в вашей системе? Если да — как отличить «оператор квитировал» от «система сама закрыла»?

8.6. Просим предоставить **примеры реальных событий**:
- 5–10 типовых тревог из журнала (неважно — архивные, анонимизированные)
- Полный lifecycle одной тревоги от появления до снятия
- Пример квитирования оператором
- Пример события при потере связи с датчиком

8.7. Есть ли события, которые **не относятся к тревогам** — диагностические, информационные, оперативные команды? Нужно ли их показывать в журнале?

8.8. Как в АПС разграничиваются «тревога» (требует реакции) и «предупреждение» (информационное)? По severity, по типу, по классу?
